# The gate

Delegation stops being a request. Second session of 2026-08-26, after the fork.

## What started it

The operator, in as many words: *we need workflow skills so I do not have to manually keep
reminding Claude Code to spawn an agent and not do things itself. It should be automatic. Baked
into its normal actions. Not a second layer, but a default.*

That is a diagnosis, not a feature request. Every rule in this repository up to this point lived
in prose, and prose is read by the one party with an interest in not following it. The core doing
the work itself is not a lapse in discipline. It is the cheapest path at every individual moment,
it feels like progress the entire time it is happening, and nothing in the tree could detect it.

## What was settled

**Three layers exist and only one is a default.**

| Layer | Enforced by | Strength |
|---|---|---|
| a `CLAUDE.md` instruction | the model choosing to comply | a request |
| a skill | the model deciding it applies | a method |
| a hook | the harness | a default |

The hook is the only one the model cannot talk past, so the hook holds the rule that most wants
breaking. `tools/hooks/card_gate.py` is a `PreToolUse` hook on `Write`, `Edit` and `NotebookEdit`.
It allows the core's own territory and anything outside the tree, and inside a working folder it
allows the write only when a played card names that folder **and** the path sits inside the
wing's chartered territory. Anything else is refused with the reason attached.

**Territory is checked, not merely written down.** `templates/CHARTER.md` already said acting
outside a charter is void rather than discouraged. Void has to mean something a person cannot
override by wanting to, and until today it meant nothing at all.

**An unfilled placeholder authorises nothing.** Upstream's placeholder sweep, given teeth: the
example card in `templates/BBS.md` grants no write anywhere, because a card carrying `<` is not
playable. `origins/the-machinery.md` records this as the extension to Pattern 8.

**It fails open, loudly.** A gate that failed closed would turn any bug in itself into a tree
nobody can edit, and the operator's only recovery would be deleting the gate, which is a worse
end state than the one being guarded against. The price of failing open is that the gate could
die silently, so it stamps `.claude/gate-last-fired` on every run and `tools/audit.py --harness`
reports what the stamp says.

**Only the harness may write that stamp.** A hand-piped test that stamped the file would make
testing the gate the thing that certified it, and the one check for silent death would pass by
being run. The payload's `session_id` is what separates the two, and a manual run leaves nothing
behind.

**The settings file is committed, never local.** `.claude/settings.json` travels with a clone.
`.claude/settings.local.json` does not, so a gate installed there is live on one device and
silently absent on every other, which is precisely the failure this arrangement exists to expose.
Both the stamp and the local settings file are in `.gitignore`.

**The skill lives at `.claude/skills/dca-delegate/`**, which is where a project skill actually
loads, rather than in a top-level `skills/` folder that would need an install step to do anything.
It carries the loop the core follows instead of working: read the router, write the card, stop,
play it, judge the return. It is never bundled into a host workspace, per upstream Pattern 9's own
exclusion of skills that are about Claude Code itself.

## What was verified rather than asserted

The gate was tested by trying to defeat it, in a sandbox tree with a real board and a real
charter. Ten cases, all behaving:

| Case | Result |
|---|---|
| core territory, no card | allowed |
| file at the tree root | allowed |
| path outside the tree entirely | allowed |
| card written but not played | refused |
| played card whose door is a placeholder | refused |
| working folder under no charter | refused |
| played card, path inside chartered territory, rung permitted | allowed |
| played card, path is the card's own `returns` | allowed |
| played card, path outside chartered territory | refused |
| played card at a rung the charter withholds | refused |

`tools/audit.py --harness` was tested in both directions: it reports the timestamp when a
harness-shaped payload has fired, and reports not live when nothing has.

**The gate is not live in the session that wrote it, and `--harness` says so.** Hooks load from
directories that already held a settings file when the session started, and this tree had none.
That is the exact condition `--harness` exists to catch, and it caught its own installation on the
first try.

## What is still open

**Spend ceilings are unenforced, and structurally cannot be here.** The Capability table is now
checked: a card sending a wing to a rung its charter withholds is refused, which closes a board
rule that had nothing behind it. Ceiling is different in kind. The gate sees a write, never a
bill, so no hook can enforce a spend cap. That belongs wherever the binding is assembled, and
nothing there is built yet.

**The gate cannot tell who is writing.** A played card opens the folder to whatever writes next,
including the core. It stops the core from working *without* a card; it does not stop the core
from playing a card and then doing the work itself. Closing that needs the woken agent to be
distinguishable from its caller, and nothing here distinguishes them yet.

**`CORE_DIRS` is a constant, and on reflection that is correct.** It was first written down here
as a defect, on the reasoning that the router already knows which folders are working folders and
a hand-maintained list drifts. That reasoning misapplied this method's own rule. Generated indexes
are rebuilt by script because they restate facts about the tree. `CORE_DIRS` is not a fact about
the tree, it is a **grant**: a declaration of which folders belong to the core. Grants are written
by hand in this method, which is the entire design of a charter, and deriving one from the thing
it governs would make the territory whatever the tree happened to contain.

What remains true is smaller: a host system whose core folders are named differently must edit
that list, and `templates/harness/README.md` says so at install.

**No wing exists.** The gate has never refused real work, because there is no chartered territory
in this tree to refuse it in. That waits on the automation wing.
