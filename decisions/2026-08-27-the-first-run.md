# The first run

The architect laid over a real tree by a session that had only the files. Session of 2026-08-27,
continuing `2026-08-27-the-architect-and-the-first-run.md`, which wrote the mandate this one
answered.

## What started it

`HANDOFF.md` and nothing else. A session was given this repository on the branch the mandate
names, the subject repository `BlueSkyGTM/albatross-engineering-os`, and no account of the two
sessions that produced the method. That was the test: whether the nuances live in the files or
lived in the room.

## The correction, and why it goes first

This run inverted the two documents and the operator corrected it in conversation. Recording that
before anything else, because it is worth more than every verdict under it.

A contract is issued in and transient. A context is emitted out and standing. Promotion spends
the contract; it does not lose it. A workspace not currently building anything holds zero
contracts, correctly, forever. The subject tree holds fifty three built folders and zero under
construction, which is a healthy steady state, and this run first reported it as that tree's most
significant defect and attached two findings to it. Both are withdrawn.

**`mechanics/the-two-documents.md` and `mechanics/the-router.md` say all of this without
ambiguity, and this session opened neither.** Both are named in `CONTEXT.md`'s routing table, one
row each. The architect skill's step 6 states the derivation correctly in a single line, and this
session read that line and drew the opposite conclusion from it, because "promoted" was taken to
require a provenance under this method rather than to mean the ordinary state of a standing
context file in place.

So the transmission verdict has to be stated carefully. **The files carried it. The session did
not follow the router it was handed.** That is a better result for the method than any prediction
below and a worse one for this session, and reporting it the other way round would have been the
easier of the two.

The residue that is genuinely the method's is one pointer: step 6 states the rule in a line and
routes to neither file that explains it. A procedure that depends on a mechanism documented
elsewhere and does not point at the explanation will be followed by someone who never reads it.

**None of the nine predictions could have caught this.** The inversion produced a finding rather
than a rename, so prediction five passed. It never touched a charter, so prediction three was
unaffected. It produced three cards whose `mode` field was confidently wrong in a way no parser
can see, because both values are valid, so prediction six passed. A run can pass eight of nine
with the core mechanism backwards.

## What was settled

**The method transmitted, and this session did not.** Six of nine predictions passed, one failed, two are not tested. The
umbrella and its floor, the charter, proposes-never-settles, the naming check, the board as a
thing written and not played, and the vocabulary that must not blur all came out the far side
intact when applied by a different model to a tree nobody designed for them. The form selection
step, named as the likeliest regression because the vendored skill opens with it, did not come
back.

**The tree yielded six wings and calls itself three.** The subject's own root router declares an
umbrella with three wings. The wing test returned six: it charters the account library, the
machinery folder and the integrations record as wings too, because each answers differently from
every other on what it may reach, what it may spend and what it must refer upward. That
disagreement, derived rather than read off, is what makes the first prediction a real pass rather
than a free one. The tree's own count was available in the first file anyone opens.

**Nothing in the tree was touched.** `tools/fingerprint.py --diff` returned ten added, zero
removed, zero changed, exit zero. Ten additions, all of them the method's own artifacts. Twelve
findings name changes that were wanted and not made, four of them renames.

**Nothing in this repository was edited.** `tools/audit.py --repo` returned clean at 295 pointers
before the run and clean after. `git status` showed no tracked file changed.

## The failure, and where it belongs

**Prediction three failed: charter fields are not all checkable.** Eight of eighteen capability
rows across the six charters carry a sentence explaining why a grant is set as it is, in the
column reserved for a restriction. No sentence describes what a wing is like, which is the
failure the rule names most directly, but justification in a checkable field is still prose with
no pass condition.

The scoring procedure asks which of two things happened, because they need opposite repairs. Both
did.

**The skill said it and the model did not do it.** The sentence is exact and it is in
`.claude/skills/dca-architect/SKILL.md`: "Every field must be checkable. Prose with no pass
condition does not belong in a charter and fails its own audit." A rule stated and ignored needs
to move down the layer table, and `tools/audit.py` does not read a charter at all.

**And the skill's own template contradicts it.** `templates/CHARTER.md` opens with the same rule
and then requires a Why column on every door, arguing that every door is a hole somebody decided
to cut and each one carries a reason, and gives the Capability table a Condition column whose own
example is a sentence. An architect obeying the rule cannot fill the template. That half is
filed, and it is the half worth having.

## What the run could not test, and why that is the finding

**Prediction nine, the gate.** It never fired. Three reasons, and every one of them is more
useful than the prediction would have been.

The subject tree has no gate, because installing one is the last step and the step before it is
the operator granting the charters. That order is correct and it means a run that stops at
proposal cannot test the gate at all.

This repository cannot test it either. Files at the root are core to the gate without being
listed, and `CORE_DIRS` covers every folder that exists here, so there is no path in this
repository where a played card is required. The only refusal it can produce here is the woken
agent wall.

And the hook is registered on three tools. A write made through a shell is a tool call, is not
one of those three, and never reaches the gate. The session running this was configured to work
through a shell, and after its first file every write went that way. Under a live gate over that
tree, one write in ten would have been seen. **That is the run's most consequential result**,
because the gate is the one layer this method describes as a default rather than a request, and
it is defeated by a configuration nobody chose against it.

**Prediction two, consolidation.** Recorded not tested, which `handoff/known-limits.md` already
said was a real answer. The on-face check ran across all fifteen pairs and found no identical
pair. Every charter was written that morning and none has been amended, so the substantive claim
had nothing behind it.

## The one silence worth an edit

`mechanics/the-two-documents.md` describes promotion and never says what becomes of the issued
`CONTRACT.md` afterwards. Kept beside the standing context, archived, or removed. `mechanics/the-router.md`
is silent too, and `CLAUDE.md` says superseded files are archived with a dated note and never
deleted, which points at one answer without settling it.

It is not cosmetic, because `audit_folder` in `tools/audit.py` runs the issued-versus-emitted diff
inside a branch requiring both files to exist, and `mechanics/acceptance.md` names that diff as the only
mechanical check for fit anyone has.

Remove the contract at promotion and the branch is never taken on any built folder, so the one fit
check retires itself the moment a folder is accepted, with no finding and no exit code. Keep it
and the same branch runs on every later audit of that folder, requiring every path issued as
available to keep appearing in the emitted inputs table forever, so maintaining a built folder
starts producing findings against a mandate that was already spent.

Filed, not resolved. One sentence in the Promotion section settles it, and whichever branch
follows should be explicit rather than implied by a file's presence.

## What the run found in the instruments

`tools/audit.py` returned 1221 findings on the subject tree, exit one. Re-resolving the same
pointers against the roots that tree actually has, a vendored workspace, two account roots, a
template root and seven installed skill roots, leaves 312, and most of those are historical
migration records correctly naming paths in the repository the tree was extracted from. Roughly
three quarters of what the audit reported is the resolver seeing two roots in a tree that has
more. Its docstring names three places a real defect could hide and this is a fourth.

`tools/fingerprint.py` reported `untouched_days` as 0.0 for all 100 folders, because a clone sets
every modification time to the moment of the clone and the tool does not read git, which it
states and defends. The architect's first step asks what has not been touched in a long time and
the reverse consolidation test asks for a wing with no work against it for a long stretch. On a
cloned tree, which is how a session usually meets one, the only instrument for both questions
returns the same number everywhere and does not say it is blind. `handoff/known-limits.md` lists
four things that tool cannot see and this is not among them.

`tools/hooks/card_gate.py` resolves a charter from the target path and never from the wing the
card names. Demonstrated on a scratch tree: a card reading wing A, whose charter withholds the
build rung, opened a folder in wing B at the build rung and was allowed, because wing B's charter
permits it. The same card aimed at its own wing was refused. `templates/BBS.md` says a wing that
may not reach a rung cannot be sent there by a card and that the gate refuses rather than
trusting the rule. That sentence is exact and the code does not implement it.

## What is still open

**Twenty three findings, none ruled.** Twelve about the subject tree, eleven about this method,
and two withdrawn and kept on the record. They
are in the subject repository at its root, in the file the findings template names, because that
is where the template says that file goes.

**The two artifacts a run emits have no address in this method.** The mandate says to write an
emitted context file and a findings file beside it. The findings file has a home; the emission
does not, and the obvious home is the one place the gate refuses, because a new folder at the top
of a tree is a working folder until `CORE_DIRS` is edited. Editing it during a measured run is
the one thing the run forbids. This run put the emission at the root of the subject tree under a
name that does not collide with the router already there, and said so on its face.

**Whether the charter template's two prose columns stay.** Naming them exempt and dropping them
are both repairs and they point opposite ways.

**Nothing has been played, and nothing has been run at any rung.** Unchanged. The build rung had
no reachable model on the machine this ran on: no key was present, and the vendor host is outside
the egress allowlist, which returned 403 at the proxy before any request left. The probe reports
that as a configuration error, exit two, which is the correct answer. Three cards are written and
all three are at rung zero, and the entry on the board says why none is at build.

**What comes after.** Still not planned, and now there are results to plan it from.
